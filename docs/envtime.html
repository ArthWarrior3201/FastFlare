EnvTime, time by majority vote

Asks several public time servers over NTP, drops any that disagree with the majority, and serves the agreed time over HTTP for any time zone and over NTP so Windows can use it as a time server.

How it stays precise

  • Parallel queries. Each round asks every upstream (default: time.google.com, time.apple.com, time.windows.com, time.cloudflare.com, time.nist.gov, pool.ntp.org) at once.
  • Doesn't wait for slow ones. As soon as 3 have answered, it gives the rest 60 ms, then leaves any still pending. A hard 1.2 s limit applies if fewer answer.
  • Majority vote. It takes the median offset. Any provider further from it than 50 ms (plus half its own round trip) is kicked for that round only and will be asked again next round. No majority means the round is discarded and the previous time keeps running.
  • Latency compensation. Every sample uses the NTP four-timestamp offset ((T2-T1)+(T3-T4))/2, which cancels the network delay.
  • Always tracking. A background loop re-syncs about every 32 s with jitter, and a request just reads the live clock (monotonic time plus the tracked offset and drift). Answering needs no network call, so a request is served in microseconds and can't be slowed or made inaccurate by upstream latency. Add ?fresh=1 to force an extra round (rate-limited to one per 2 s).
About time.is. It is a website, not an NTP server, so it can't be part of the vote. Web time checks only have one-second resolution, which is too coarse to outvote NTP servers accurate to milliseconds. Add more NTP hosts with FF_TIME_PROVIDERS instead.
Expected accuracy. Typically a few milliseconds over a normal internet connection. The uncertaintyMs field in every reply is the honest bound for that moment. It is not atomic-clock timekeeping.

HTTP API

GET /time?tz=Asia/Kolkata

{
  "unixMs": 1795347120123,
  "unix": 1795347120,
  "utc": "2026-11-22T09:32:00.123Z",
  "timeZone": "Asia/Kolkata",
  "abbreviation": "GMT+5:30",
  "offsetMinutes": 330,
  "local": "2026-11-22T15:02:00.123+05:30",
  "synced": true,
  "uncertaintyMs": 4.3,
  "sources": { "used": ["time.google.com", "time.apple.com", "time.windows.com"], "kicked": [] }
}

tz is any IANA zone (America/New_York, Europe/London, UTC). It defaults to UTC. Unknown zones return 400. GET /time/status shows the last round: which providers were used, kicked, failed or skipped as slow, the tracked offset and drift.

Use it as your Windows time server

Windows speaks NTP on UDP port 123 only, so FastFlare's NTP server must listen there. Run it on a Linux host or container with that port reachable:

docker run -d --name fastflare -p 8787:8787 -p 123:123/udp -e FF_SECRET=... fastflare
# or: sudo setcap 'cap_net_bind_service=+ep' $(which node)  &&  node src/server.js

Then, in an administrator Command Prompt on the Windows machine (replace the host):

w32tm /config /manualpeerlist:"time.example.com,0x8" /syncfromflags:manual /reliable:no /update
net stop w32time && net start w32time
w32tm /resync /force
w32tm /query /status
w32tm /stripchart /computer:time.example.com /samples:5 /dataonly

The last command prints the offset between that PC and FastFlare, so you can see it working. Don't run FastFlare's NTP server on the same Windows machine as w32time: both want UDP 123. Run it elsewhere (a small VPS or a Linux box).

Linux with chrony: add server time.example.com iburst to chrony.conf.

Until the first round succeeds, the NTP server answers as "unsynchronized" (stratum 16), so clients ignore it instead of trusting a guess.

Configuration

VariableDefaultMeaning
FF_TIME_PROVIDERSthe six aboveComma-separated host or host:port.
FF_TIME_MIN_VOTES3Answers needed before the grace window starts.
FF_TIME_GRACE_MS60Extra wait for stragglers after the minimum is met.
FF_TIME_TIMEOUT_MS1200Hard limit for a round.
FF_TIME_TOLERANCE_MS50How far from the median a provider may be before it is kicked.
FF_TIME_POLL_MS32000Background re-sync interval. Public servers rate-limit abusive polling, so don't set this too low.
NTP_PORT / FF_NTP=0123UDP port for serving NTP, or disable it.

Google's time servers "smear" leap seconds while others step them. Around a leap second they can disagree by up to half a second; the majority vote handles that by kicking the odd ones out.
